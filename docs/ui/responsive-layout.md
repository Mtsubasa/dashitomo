# Flutter レスポンシブUI設計方針

だしトモのAndroid・iOS画面を、画面密度、画面サイズ、縦横比、Safe Areaが異なる環境でも同じ構図と操作性で表示するための方針。

## 基本原則

- 端末名、OS、phone / tabletの分類ではなく、Widgetが親から受け取る制約を基準にレイアウトする
- 画面全体は`MediaQuery.sizeOf`、コンポーネントが利用できる大きさは`LayoutBuilder`の`BoxConstraints`から取得する
- 背景など欠けても情報を失わない装飾はSafe Areaの外まで描画し、操作要素と重要情報は`SafeArea`内へ置く
- デザイン基準サイズは比率を求めるために使用し、画面全体を固定キャンバスとして一括拡大しない
- 固定値は画面座標ではなく、親内の比率、基準サイズからのscale、`min` / `max`制約として使用する
- 見た目とタップ領域を分離し、操作要素は48×48 logical pixels以上を確保する
- 画面回転やウィンドウサイズ変更で再計算される、状態を持たないレイアウトにする

Flutterのlogical pixelが画面密度差を吸収するため、独自にdevicePixelRatioを掛けない。主に利用可能なlogical size、縦横比、Safe Area、文字倍率の差へ対応する。

## 画面構成

ビジュアル中心の画面は、固定座標の一枚の`Stack`ではなく役割ごとの領域に分ける。

```text
画面
├── 背景（Safe Area外、BoxFit.cover）
└── SafeArea
    └── LayoutBuilder
        ├── Top領域（上端へ固定）
        ├── Content領域（残り高さへ追従）
        └── Bottom領域（下端へ固定）
```

- Top / Bottomは必要な最小サイズを優先する
- Contentは残り領域を受け取り、幅と高さの小さい方を上限に子を`BoxFit.contain`で配置する
- 高さ不足時は外側余白、領域間余白、Content内の装飾の順に縮め、操作要素や重要情報を先に縮めない
- 大画面では`ConstrainedBox`で最大幅を制限し、要素を無制限に拡大しない

## アセットと重ね要素

画像に文字、進捗、アイコンなどを重ねる場合は、一つのコンポーネントとして親子関係を作る。

```text
SizedBox（アセットの表示サイズ）
└── Stack
    ├── Positioned.fill（基準アセット）
    └── 子要素（親の幅・高さに対する割合で配置）
```

- アセット固有の座標は`0.0`〜`1.0`の割合で定義する
- 子要素の位置とサイズは親の実サイズに割合を掛けて算出する
- 親のアスペクト比を維持し、画像だけを異なる比率へ変形しない
- 進捗表示は背景トラックの矩形を割合で定義し、進捗率だけを横幅へ掛ける
- 複数要素が一つの装飾を構成する場合、個別に画面へ`Positioned`せず専用Widget内でまとめる

ホーム画面ではネームプレートと内部表示を`TopHud`、タブ枠と各タブを`BottomNavigation`として管理する。メニューはTop領域を基準に置き、画面外へ出さない。

## scaleの管理

デザイン基準幅を`referenceWidth`として一か所に定義し、コンポーネントのscaleを次の考え方で求める。

```text
scale = clamp(availableWidth / referenceWidth, minimumScale, maximumScale)
```

- scale計算はView内のレイアウト専用クラスへ集約する
- 色、基準寸法、アセット内の割合座標は定義クラスに置く
- ViewModelへ画面サイズ、`BuildContext`、レイアウト値を持たせない
- scale済みの値と未変換の基準値を同じWidget内で混在させない
- 文字倍率を尊重する。画像内の短い装飾文字だけは`FittedBox(fit: BoxFit.scaleDown)`でoverflowを防ぐ

## ブレークポイント

構成が同じまま縮尺だけ変わる画面では連続的な制約計算を優先し、細かなブレークポイントを作らない。レイアウト自体を変更する場合だけ、利用可能幅または高さを基準にcompact / regularなど少数の区分を設ける。端末種別、OS、画面の向きだけでは分岐しない。

## Webプレビュー

Webは開発・Pull Request確認用であり、単一の402×755表示だけを端末検証の代わりにしない。

- 基準比較には402×755を使い、追加で小型、標準、縦長のviewportを確認する
- Web用フレームが`MediaQuery.padding`をゼロにする場合、Widget testでSafe Areaありのケースを検証する
- Webだけに合わせた条件分岐をホーム画面へ入れない

## テスト

主要画面は320×568、360×640、390×844、402×755、412×915、430×932のlogical sizeを最低限確認する。

- Flutterのoverflow例外がない
- Top / Content / Bottomが順序を保ち、相互に重ならない
- 操作要素がSafe Area内にある
- 主要操作のタップ領域が最低サイズ以上である
- 文字倍率を上げても重要情報が欠けない

基準サイズは必要に応じてgolden testで視覚的な退行も検出する。goldenだけに依存せず、境界、重なり、タップ可能性をWidget testでも検証する。

## レビュー時チェック

- [ ] 画面全体の絶対座標で画像内要素を配置していない
- [ ] アセットと重ね要素が同じ親Widgetで拡縮される
- [ ] `LayoutBuilder`を必要なローカル制約の位置で使っている
- [ ] 背景と重要コンテンツでSafe Areaの扱いを分けている
- [ ] 小型・基準・縦長サイズのテストがある
- [ ] 固定値が基準寸法・割合・最小操作サイズのどれかとして説明できる
